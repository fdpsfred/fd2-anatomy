# Watcom Easy OMF-386 目標檔格式 quirks

Watcom 9.5a 產出的 `.obj`（wcc386 的 output、CLIB3S / MATH387S 等 vendor lib 內的成員）是
**Easy OMF-386** 格式：Intel OMF 的 32-bit 擴充版。要正確 parse 這些 `.obj`（例如抽 PUBDEF
名稱 / segment offset / function size 做 CRT FID 比對，或抽 LEDATA + FIXUPP 位置做 byte-level
match），必須處理幾個偏離標準 16-bit OMF 的地方。本文件是讀寫這類 `.obj` 共用的格式結論；下述
每一條都對應到 `tools/program_analysis/crt_callee_match/` 內已驗證的 OMF parser 實作。

## Record type：16-bit 與 32-bit 兩種形式

Easy OMF-386 對「含 offset / length 欄位」的 record 各有 16-bit 與 32-bit 兩種 type，32-bit
形式 = 16-bit type ID 的最低位設 1：

| Record | 16-bit type | 32-bit type | 32-bit 形式的差異 |
|---|---|---|---|
| SEGDEF | `0x98` | `0x99` | SegLen 由 2 byte 變 4 byte |
| PUBDEF | `0x90` | `0x91` | public symbol 的 offset 由 2 byte 變 4 byte |
| LEDATA | `0xA0` | `0xA1` | data record 的 segment offset 由 2 byte 變 4 byte |
| FIXUPP | `0x9C` | `0x9D` | target displacement 由 2 byte 變 4 byte |
| MODEND | `0x8A` | `0x8B` | -- |

不含 width-sensitive 欄位的 record（`THEADR 0x80`、`LNAMES 0x96`）沒有 32-bit 變體。

Record 通用框架：`type(1) | record_length(2, LE) | body(record_length-1) | checksum(1)`。
Parse 到 MODEND（`0x8A` / `0x8B`）即停。

## Quirk 1：32-bit 內容藏在 16-bit record type `0x98` 之下

Watcom Easy OMF-386 有時把 32-bit 內容寫在 16-bit 的 `0x98` SEGDEF type 底下（不改成
`0x99`）。判別這種「quirky」檔的方法是看第一個 SEGDEF：

- SEGDEF body 標準 16-bit layout 是 `ACBP(1) | [絕對段 FrameNum(2)+Offset(1)] | SegLen(2) |
  NameIdx | ClassIdx | OvlIdx`。
- 對 `type == 0x98` 且 record_length >= 9 的 record，檢查 body 的第 4 個 byte（`body[3]`）。
  標準 16-bit 下那個位置是 NameIdx（必須 >= 1）；若它 == 0，代表 SegLen 其實是 4 byte（把
  NameIdx 往後推了 2 byte），也就是這個檔是 quirky 的 32-bit 檔。

**一旦判定 quirky，整個檔所有 record 都用 32-bit 寬度欄位**：SegLen 4 byte、PUBDEF offset
4 byte、LEDATA offset 4 byte、FIXUPP displacement 4 byte。判定條件：`use32 = (record type 是
0x99 / 0x91 / 0xA1 / ...) OR quirky`。

## Quirk 2：ACBP 的 P-bit 不可信，段寬要靠 record type / quirky 推

標準 OMF 用 SEGDEF 的 ACBP byte（bit0 = P，或 B「big」bit）判 segment 是否 USE32。在 Watcom
Easy OMF-386 這個 bit **不可信**。要判 segment 是不是 32-bit（USE32），改用：record type ==
`0x99`（SEGDEF32），或整檔 quirky。CLIB3S 這類 Watcom 32-bit lib 的 USE32 segment 就是靠這兩
個訊號辨識，不是靠 P-bit。

## Quirk 3：FIXUPP LOCAT 是 10-bit offset

FIXUP subrecord（LOCAT 的 bit7 = 1；bit7 = 0 則是 THREAD subrecord，要另外跳過）開頭 2 byte
是 big-endian 的 LOCAT：

```
byte0:  1 M LLLL OO      bit7=1 (FIXUP)、bit6=M (mode)、bits5..2=location_type(4 bit)、bits1..0=offset 高 2 bit
byte1:  OOOOOOOO         offset 低 8 bit
```

data_record_offset 是 **10-bit**：`((byte0 & 0x3) << 8) | byte1`。緊接 1 byte 的 fix_data
（F / Frame / T / P / Targt 欄位），再依 F / T / P 決定是否還有 frame index、target index、
target displacement。

## Quirk 4：32-bit segment 內 location_type 1 / 5 是 4-byte fixup

standard OMF 各 location_type 的 fixup 寬度：

| location_type | 意義 | 標準寬度 |
|---|---|---|
| 0 | lobyte | 1 |
| 1 | offset16 | 2 |
| 2 | base（segment）| 2 |
| 3 | ptr16:16 | 4 |
| 4 | hibyte | 1 |
| 5 | offset16（LE 變體）| 2 |
| 6 | ptr16:32 | 6 |
| 9 | offset32 | 4 |
| 11 | ptr16:32（alt）| 4 |
| 13 | offset32（LE 變體）| 4 |

Watcom 32-bit lib（CLIB3S 等）與 quirky 檔的 USE32 segment 有一個關鍵偏差：**location_type
1 / 5 實際上是 32-bit（4-byte）offset**，即使 type ID 沿用標準 16-bit 的編碼（不改成 9 / 13）。
所以 parse fixup 寬度時，若目標 segment 是 USE32（見 Quirk 2），要把 location_type 1 / 5 從
2 byte 放大成 4 byte，否則會漏 patch 4-byte offset 的後半段。

同理，target displacement（fix_data 的 P = 0 時存在）在 quirky / 32-bit 檔是 4 byte（標準
16-bit 是 2 byte）。

## Function size 的算法

從 PUBDEF 抽出的每個 public symbol，其 function size = 同一 code segment 內「下一個 PUBDEF
offset（按 offset 排序）」減本 offset；最後一個 symbol 用 segment length 減本 offset。code
segment 的判別 heuristic：class 名含 `CODE`，或 segment 名以 `_TEXT` 結尾 / == `CODE`。

## 除錯陷阱

比對 FD2 binary 與 lib `.obj` 的 function bytes 時，FIXUPP 位置要用 wildcard mask（fixup 過的
byte 在 link 後會被 relocate，不能直接比）。若看到 mismatch 集中在某段 4-byte 區域，第一個懷疑
點是 Quirk 4 的 32-bit fixup 寬度沒抓對（把 location_type 1 / 5 當成 2-byte 而漏 wildcard 後
半段）。
